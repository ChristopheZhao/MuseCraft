# Plan: Backend database and agent persistence boundary decoupling

- Type: fix
- Status: in_progress
- Priority: P0
- Owner: codex

## 1. Current Problem
- Symptom:
  - The production Agent contract imports SQLAlchemy `Session` and ORM `Task`, and `BaseAgent.execute(...)` passes both through every specialist Agent invocation.
  - Production Agent code still performs persistence work. `QualityCheckerAgent` mutates an ORM task and commits, while `EpisodeOrchestratorAgent` creates and commits ORM tasks. Other Agent modules retain ORM types or dead persistence helpers.
  - Celery queue modules create engines and sessions, query ORM entities, evaluate execution eligibility, prepare runtime dispatch, mutate task state, and pass a live session into the MAS execution host.
  - Runtime control-plane semantics are correctly assigned to `RuntimeSessionService`, but that owner is fused with SQLAlchemy queries, transactions, ORM entities, and read-model serialization.
  - Database URL/dialect decisions are duplicated across core database setup, queue modules, Alembic, legacy startup, and the dirty uv launcher change.
  - Existing governance documents claim that Agent/Session coupling was removed, while current production code and tests still preserve it.
- Impact:
  - Agent reasoning and media algorithms cannot run or be tested independently from the backend ORM contract.
  - Persistence failures and transaction behavior can alter Agent trajectories, and Agents can mutate business/runtime state outside the control-plane boundary.
  - Queue/worker transport remains coupled to runtime and persistence decisions, contradicting Runtime SoT ownership and external-scheduler decoupling.
  - Local and production database configuration cannot evolve through one composition boundary; provider-specific checks drift between entrypoints.
  - The release can appear database-agnostic while only one migration/transaction profile is actually verified.
- Reproduction/evidence:
  - `backend/app/agents/base.py` imports `Session` and ORM `Task`; both are part of `execute` and `_execute_impl` signatures.
  - `backend/app/agents/quality_checker.py` writes quality fields and calls `db.commit()`.
  - `backend/app/agents/episode_orchestrator.py` creates ORM `Task` rows and commits workflow status changes.
  - `backend/app/services/task_queue.py` and `project_job_queue.py` create duplicate engines/session factories and own ORM-backed dispatch setup.
  - `backend/app/services/queued_task_execution_host.py` passes ORM `task` and `db` into current production orchestrators.
  - Static audit found persistence/ORM boundary references in 15 production Agent files and no capability-oriented runtime/task persistence port covering this path.

## 2. Deviation Analysis
- Expected behavior:
  - Entry points (`uv`, Docker, API, Celery) select configuration and call application use cases; they do not own database-provider policy or MAS runtime semantics.
  - Agent and algorithm code consumes immutable domain execution contracts, ContextAssembler output, Memory services, and registered tools. It emits typed Agent results and boundary events without importing ORM models or receiving a database session.
  - Runtime/session/node/attempt/gate/decision semantics remain exclusively owned by the MAS control plane.
  - The control plane persists authoritative runtime facts through capability-oriented store interfaces whose implementations own SQLAlchemy and transaction details.
  - Local and production profiles use the same application contracts. Local is the default development target; production requires explicit connection configuration and never falls back to local credentials.
  - Database support is truthful: a provider is supported only when its migration chain and required transaction semantics are tested. Supporting one provider does not weaken architectural decoupling.
- Actual behavior:
  - ORM entities and live sessions cross the queue, execution-host, orchestrator, BaseAgent, and specialist-Agent boundaries.
  - Some Agents commit transactions directly; other Agents retain database-shaped method contracts even when they do not use the session.
  - `RuntimeSessionService` owns the correct semantics but also acts as a large concrete SQL repository and projection builder.
  - The uv launcher dirty change interprets the database backend and enforces PostgreSQL policy in the launcher layer.
  - PLAN-050 still describes MySQL-authoritative transaction evidence while PLAN-067 and release CI select PostgreSQL; PostgreSQL migration smoke does not prove control-plane lease/gate concurrency semantics.
- Root cause:
  - Earlier refactors removed specific DB writes and memory fallbacks but preserved the original ORM-shaped execution API for compatibility.
  - Runtime ownership and physical persistence were treated as one service implementation instead of two boundaries connected by a transactional port.
  - Queue and startup scripts accumulated bootstrap logic independently rather than consuming a shared composition root.
  - Tests protect behavior and historical call signatures but do not enforce import direction or layer ownership.

## 3. Boundary Contract

### 3.1 Required dependency direction
```text
uv / Docker / API / Celery
          |
          v
Application use cases / MAS control plane
          |
          v
TaskStore / RuntimeStateStore / UnitOfWork contracts
          |
          v
SQLAlchemy persistence adapters
          |
          v
Configured local or production database
```

```text
AgentExecutionRequest + assembled context + memory + tools
                         |
                         v
                       Agent
                         |
                         v
AgentResult + orchestration_report + typed boundary events
```

### 3.2 Ownership rules
- Agent/algorithm owns planning, tool selection, evidence interpretation, reflection, and explicit boundary reporting.
- MAS control plane owns runtime decisions and authoritative session/node/attempt/gate/decision transitions.
- Application use cases own task lifecycle coordination and transaction boundaries around business commands.
- Persistence ports express domain-specific atomic capabilities; they must not become generic CRUD repositories that hide lease/gate semantics.
- SQLAlchemy adapters own ORM mapping, engine/session creation, dialect adaptation, and transaction implementation.
- Read-model query adapters own API projections; API and frontend do not infer runtime state from queue health.
- Startup entrypoints own process lifecycle only. They call a shared database preflight/migration boundary and render its typed diagnostics without choosing provider policy.

### 3.3 Local and production configuration
- Local development is the default documented profile and targets a local address through the root project configuration.
- Production requires an explicit production profile and database URL/credentials; missing production configuration fails closed.
- PostgreSQL remains the only required release adapter until another adapter has a tracked migration chain plus runtime transaction evidence.
- MySQL branches are not considered support by themselves. Legacy MySQL adoption remains a reviewed schema/data migration concern and must never be silently stamped or auto-converted.
- An embedded SQLite profile is out of scope for full multi-process MAS runtime until its capability limits are explicit. It may be considered later for a bounded single-process demo profile.

### 3.4 Amendment A1 - Operational Agent/SQL decoupling clarification
- Amendment date: `2026-07-19`.
- Corrected verdict: the direct Agent execution contract is database-free, but the operational dependency boundary is not yet closed. Production Agents no longer accept ORM entities or sessions, while several Agent import/construction paths still reach SQLAlchemy composition transitively through concrete services and global repositories.
- Agent purity applies to the transitive runtime dependency graph, not only imports physically located under `app/agents`:
  - importing or constructing a production Agent must not initialize an engine/session factory or require a configured database;
  - an Agent may depend on a domain/application port, but it must not import or construct the SQLAlchemy implementation of that port;
  - concrete persistence adapters are registered only by an application composition root outside the Agent package.
- SQL remains a backend infrastructure module. Full API/worker startup may require PostgreSQL because the product exposes durable task/runtime/project behavior; this requirement is not itself Agent coupling. The required separation is that database failure surfaces at bootstrap or the application persistence boundary before Agent invocation, rather than as an Agent reasoning failure.
- Persistence services are capability-oriented domain ports, not a generic SQL/CRUD service exposed to Agents. Test-only in-memory implementations must be explicitly injected and must never become a production fallback.
- Historical Gate B and Gate D evidence remains valid for direct signature cleanup, domain contracts, control-plane ownership, and store-command semantics. It no longer proves complete Agent/database independence until Amendment A1 closes.

### 3.5 Amendment A2 - Runtime authority decomposition and owner freeze
- Amendment date: `2026-07-19`.
- A2 supersedes three ambiguous parts of A1: a mixed `ProjectStateStore` is not an acceptable persistence port; `EpisodeOrchestratorAgent` has no remaining native-Agent escape clause; and runtime transition invocation ownership must be explicit rather than described only as facade injection.
- Authority is split by meaning:
  - a versioned project-definition aggregate owns authored series/episode plans, editorial approvals, project configuration, and budget constraints;
  - the MAS runtime control plane exclusively owns episode/workflow execution status, workflow/session/node/attempt/gate identity, retry/lease facts, and terminal transitions;
  - published deliverables own accepted output references; usage/accounting records own observed token and cost facts;
  - a read-only project-execution projection may join those authorities for API/UI consumption, but it cannot be saved back as project authority.
- `ProjectState`, `EpisodeRuntimeState`, `episodes_runtime`, `workflow_task_id`, generated output assets, observed totals, progress, and completed counts must not be moved unchanged behind a newly named store. The mixed aggregate is decomposed and the incorrect persisted runtime fields are removed through an explicit migration/normalization step, without a dual-write or silent compatibility path.
- `SeriesPlannerAgent` remains a reasoning component that returns a typed plan draft. A project application use case applies that draft to the versioned project-definition aggregate through a capability-oriented port and unit of work.
- `EpisodeOrchestratorAgent` is replaced by a deterministic application/control-plane coordinator outside the production Agent registry. It must not inherit or advertise native-Agent execution semantics while running a fixed episode pipeline and mutating project/runtime state.
- `OrchestratorAgent` is classified as a MAS control-plane coordinator, not a specialist native Agent. It may select semantic runtime actions only through the database-independent control-plane contract; the application composition root injects runtime ports, while SQLAlchemy adapters and transaction construction remain outside its dependency graph.
- Project writes use explicit optimistic concurrency. Every mutation carries an expected version and either commits atomically or returns a typed conflict; callers must not perform blind last-write-wins retries.
- A2 remains bounded to ownership, persistence, and contract-boundary correctness. Authentication belongs to PLAN-067 release security; shared WorkingMemory/EventBus storage requires a later provider-neutral port decision; broad monolith splitting remains deferred until owners are stable.

## 4. Implementation Approach
- Patch strategy:
  - Use strangler-style contract migration rather than a big-bang rewrite. Introduce new domain/application contracts first, migrate one production path at a time, and delete the old ORM-shaped path as soon as each slice is accepted.
  - Preserve the dedicated runtime control-plane services as semantic owners while moving physical storage operations behind injected runtime-store contracts; do not restore the deleted aggregate `RuntimeSessionService`.
  - Move Task/Scene/quality persistence out of Agent methods into application/control-plane handlers consuming explicit Agent results or boundary events.
  - Replace queue-owned bootstrap semantics with one application execution use case that accepts stable identifiers and injected ports.
  - Centralize database profile resolution, engine/session factories, migration strategy, and typed preflight diagnostics in infrastructure composition.
  - Amendment A2 executes before release closure: freeze the authority split, decompose mixed project/runtime state, move the deterministic episode coordinator to the application/control-plane layer, and inject runtime ports into the MAS control-plane coordinator.
- Compatibility considerations:
  - Runtime SoT must remain in the control plane; it must not be moved into Shared WM, episodic memory, Celery state, websocket state, or artifact existence.
  - Existing continuation, gate, lease, published-deliverable, and scene-output acceptance contracts must remain fail closed.
  - Agent output meaning and autonomous ReAct behavior must not be rewritten as part of persistence extraction.
  - Existing local databases are not modified during contract migration without an explicit migration/backup step.
  - PostgreSQL-specific transaction behavior must be validated before public runtime claims are updated.
- Scope out:
  - No prompt-only workaround, README-only packaging, or provider-name branch inside Agent code.
  - No requirement to support every SQL database.
  - No automatic migration of the existing pre-release MySQL database.
  - No replacement of SQLAlchemy solely for abstraction purity.
  - No full rewrite of unrelated CRUD endpoints before the task/runtime command and read-model paths are closed.
  - No Docker-only local workflow.
  - No authentication implementation inside PLAN-068; PLAN-067 owns the public-release authentication, callback-signature, provider-admin, websocket, and file-access security gate.
  - No mandatory Redis implementation for WorkingMemory/EventBus and no broad file-size-driven refactor before authority boundaries are accepted.
- Rollback plan:
  - Keep each slice independently reviewable and commit domain contracts, Agent migration, transport migration, runtime-store extraction, and configuration/docs separately.
  - Do not retain dual semantic owners. A temporary adapter may bridge representation only and must be deleted in the same slice that finishes its consumer migration.
  - If PostgreSQL transaction evidence fails, keep the prior runtime owner active, record the failed semantic assumption, and repair the store implementation before advancing.

## 5. Execution Contracts

### Slice A - Boundary freeze and executable dependency rules
- What: establish domain execution contracts, persistence-port responsibilities, supported database profile semantics, and automated import/ownership guards before moving behavior.
- Why: without an executable boundary, the refactor can merely rename `db` or move SQLAlchemy imports into another high-level service while preserving the same coupling.
- Done signals:
  - Agent execution input/output contracts use JSON-serializable/domain values and stable IDs, not ORM entities.
  - A dependency test rejects `sqlalchemy`, `app.core.database`, and ORM `app.models` imports from production Agent modules.
    - During the staged migration, the exact pre-existing violations are an explicit ratchet: additions and helper relocation fail immediately; Slice B must reduce the ratchet to zero.
  - The test distinguishes domain enums/contracts from ORM mappings so the solution does not rely on package naming tricks.
  - Local-default and production-explicit configuration semantics plus the verified provider matrix are documented as architecture contracts.
  - PLAN-067 no longer assigns database-provider decisions to the uv launcher.
- Evidence checklist:
  - Domain contract modules and architecture boundary document.
  - Static dependency/AST test with a focused negative fixture or equivalent regression proof.
  - Updated PLAN-067 Slice E and PLAN-068 status evidence.
- Negative cases:
  - Renaming `Session` to `Any` while passing the same object does not satisfy the contract.
  - Moving ORM imports from Agent to an Agent helper does not satisfy the dependency rule.
  - A default local profile must not be reused as an implicit production fallback.
- Suggested checkpoints: `persistence-boundary-freeze`, `dependency-rule-red-green`.

### Slice B - Agent and algorithm persistence isolation
- What: remove ORM Task/Scene/Resource types and database sessions from BaseAgent, ReActAgent, orchestrators, and every production specialist Agent.
- Why: Agent autonomy, testability, and Tools-first behavior require the reasoning loop to be independent from physical persistence and transaction failures.
- Done signals:
  - `BaseAgent.execute` and `_execute_impl` have no `db` parameter and receive an immutable Agent execution request/domain task reference.
  - No production Agent imports SQLAlchemy, `app.core.database`, or ORM entities from `app.models`.
  - Quality Checker returns a typed quality result; a downstream application handler persists the read model.
  - Project/Episode orchestration emits or invokes an application-level task command instead of constructing/committing ORM Task rows.
  - Scene/resource persistence helpers are removed from Agents or converted to pure contract construction.
  - Focused Agent tests run without creating a database engine/session or ORM Task fixture.
- Evidence checklist:
  - BaseAgent/ReActAgent signatures and all production Agent imports.
  - Quality, episode/project, concept, audio/resource, and orchestrator focused tests.
  - Static dependency test from Slice A.
- Negative cases:
  - No Agent may call `commit`, `rollback`, `add`, `refresh`, or query an ORM model.
  - No dummy Session fixture may be required to execute a pure Agent test.
  - Persistence extraction must not synthesize missing Agent outputs or orchestration reports.
- Suggested checkpoints: `agent-purity`, `agent-result-persistence-handoff`.

### Slice C - Transport-only queue and application execution host
- What: make Celery/in-process queue adapters carry stable task IDs and invoke one application execution use case without owning ORM, runtime routing semantics, or task-state transitions.
- Why: queue state is transport diagnostics, not business/runtime truth, and scheduler replacement must not change MAS semantics.
- Done signals:
  - Celery task payloads contain stable identifiers and bounded transport metadata only.
  - Queue modules do not create SQLAlchemy engines/session factories or import runtime ORM entities.
  - Eligibility, dispatch preparation, failure transition, and mode routing are application/control-plane services invoked through one execution use case.
  - Queued, in-process, and direct test hosts exercise the same application entry contract.
  - Queue outage/probe ambiguity remains diagnostic and cannot advance runtime state.
- Evidence checklist:
  - Queue adapters, execution host/use case, task execution policy, and worker tests.
  - Runtime read-model assertions showing queue metadata is not used as SoT.
- Negative cases:
  - Moving the current `SyncSessionLocal` into another Celery module does not satisfy this slice.
  - A queue result state must not mark a runtime session completed or authorize resume.
  - Worker exception handling must not swallow a failed control-plane transition into a generic success payload.
- Suggested checkpoints: `transport-only-worker`, `single-execution-use-case`.

### Slice D - Runtime control-plane store separation
- What: retain runtime semantic ownership in dedicated MAS control-plane services while extracting SQLAlchemy and transaction mechanics into capability-oriented runtime persistence adapters.
- Why: runtime authority must remain centralized, but physical SQL storage must be replaceable/testable without exposing ORM entities to orchestrator, Agent, queue, or API contracts.
- Done signals:
  - Runtime domain records/contracts are separate from SQLAlchemy mappings.
  - Runtime control-plane services and orchestration-facing facades depend on narrow injected store/unit-of-work contracts rather than a live Session.
  - Atomic store operations explicitly cover attempt start/lease/heartbeat/release, gate open/decision, continuation binding, completion/failure, and fresh read-model loads.
  - Published deliverable persistence and script-review publication no longer require ContextAssembler callers to supply a Session.
  - A SQLAlchemy PostgreSQL adapter implements the required operations without changing runtime decision ownership.
  - Runtime API projections are returned as explicit read models, not ORM entities.
  - The legacy aggregate `RuntimeSessionService` is removed rather than retained as a compatibility surface.
- Evidence checklist:
  - Runtime state contracts, store interface, SQLAlchemy adapter, control-plane service/facades, and projection adapter.
  - Existing PLAN-066 boundary suite plus new store contract tests.
- Negative cases:
  - Runtime authority must not move into MemoryWriter, Shared WM, events, queue state, or a generic repository callback.
  - Store adapters must not choose orchestration actions or invent missing contract facts.
  - Returning ORM objects through a protocol typed as `Any` does not count as separation.
- Suggested checkpoints: `runtime-store-contract`, `control-plane-owner-preservation`, `read-model-separation`.

### Slice E - Database composition and local/production profiles

- Suggested checkpoints: `database-composition-root`, `local-production-profile`, `migration-preflight-owner`.

### Amendment A2 - Project authority, runtime SoT, and boundary-transparency closure
- What: replace the mixed project/runtime aggregate with separate write authorities and a read-only projection; make project mutations versioned and atomic; freeze coordinator identities and runtime transition ownership; close the audited fail-open context/tool/contract boundaries that could hide an ownership violation.
- Why: implementing A1 literally would put `episodes_runtime`, workflow IDs, output assets, progress, and observed costs behind a `ProjectStateStore`, preserving a second Runtime SoT. The same audit found an unresolved deterministic-Agent identity, unspecified transition caller ownership, last-write-wins project saves, context assembly side effects, and fail-open contract/tool visibility behavior.
- Semantic closure:
  - `ProjectDefinition` (final name may follow established domain naming) is the only project write aggregate and contains authored/editorial facts plus configured constraints; it contains no live runtime status, workflow identity, generated assets, observed usage, or derived progress.
  - `ProjectExecutionReadModel` is assembled from project definition, workflow runtime, published deliverables, and an explicit usage owner. It is immutable and query-only; API serialization never calls a save operation.
  - Project commands run in an application unit of work and save with `expected_version`. A stale version returns a typed `project_version_conflict` and leaves every authority unchanged.
  - The deterministic episode coordinator is an application/control-plane service invoked directly by project execution use cases. It is removed from native-Agent allocation/registration and receives typed project/runtime ports through construction.
  - The MAS orchestrator is explicitly classified as control-plane logic. It decides transitions through `RuntimeSessionControlPlane`/narrow runtime ports; the execution host wires those ports but does not choose workflow semantics, and no Agent/control-plane module constructs a SQLAlchemy facade.
  - Context assembly is read-only. Scene-reference or deliverable persistence occurs before assembly through an application/control-plane command, and the assembler consumes the resulting typed reference.
  - ReAct plan-contract conflict evaluation and contract-overlay failures return typed diagnostics and halt the affected decision path; they never default to `conflict=False` or `pass`.
  - Tool FC visibility evaluation fails closed (`expose=False`) with a diagnostic. Optional memory write failure may still degrade by policy, but returns a typed receipt with reason code instead of an untyped `None`.
  - Vendor-specific clients remain infrastructure/tool adapters. Agent allocation and prompts consume supplier-neutral capabilities; replacing the music provider does not require changing Agent code or allocation identifiers.
- Done signals:
  - No project authority schema or domain write model contains `episodes_runtime`, runtime status, workflow/session IDs, generated output assets, observed token/cost totals, or derived completion counts.
  - Project runtime API responses are produced by a query projection backed by runtime/deliverable/usage ports, and no read path writes project state.
  - Two concurrent project commands using the same version yield one commit and one typed conflict; no field update is silently lost and no partial runtime/project write remains.
  - `EpisodeOrchestratorAgent` is absent from the production Agent registry and fixed episode sequencing is owned by an application/control-plane coordinator with explicit ports.
  - Importing and constructing specialist Agents plus the MAS orchestrator under sentinel-invalid database configuration performs no engine/session/store construction.
  - Runtime transition tests prove the MAS control plane selects every transition while the composition root only injects implementations and scopes transactions.
  - Context assembly performs no filesystem/database/reference write, ReAct contract failures halt with typed diagnostics, and tool-visibility exceptions expose no function calls.
  - Music generation is allocated by a supplier-neutral capability/tool contract; the Suno implementation, if retained, is selected only by provider configuration.
- Evidence checklist:
  - Authority matrix and migration note covering every field removed from the mixed `ProjectState` payload.
  - Static AST/import-graph guard rooted at every production Agent/control-plane entrypoint, with negative fixtures that hide a forbidden dependency behind a service/facade.
  - Dynamic import/construction test with engine/session/store sentinels that fail on any composition or connection attempt.
  - Versioned project port, SQLAlchemy adapter, unit-of-work, concurrent stale-write, rollback, and read-model tests.
  - Agent identity/allocation tests for specialist native Agents, deterministic stages, application coordinators, and the MAS control-plane orchestrator.
  - Runtime transition ownership, ContextAssembler purity, ReAct fail-closed, tool-visibility deny-by-default, typed memory receipt, and supplier-neutral music allocation tests.
  - Existing PLAN-066 boundary regressions, runtime-store/control-plane suites, full unit/architecture suites, and `git diff --check`.
- Negative cases:
  - Renaming the existing mixed `ProjectState` repository or projecting its persisted `episodes_runtime` blob does not close Runtime SoT ownership.
  - A read model with `save`, `update`, or mutation side effects is forbidden.
  - Timestamp-only last-write-wins, blind retry after conflict, or independent project/runtime commits without compensation/UoW are forbidden.
  - Keeping `EpisodeOrchestratorAgent` in the Agent registry with a different execution-mode label does not count as reclassification.
  - Moving SQL construction behind an Agent-imported service/factory does not satisfy dependency closure.
  - Logging and continuing after a contract-conflict evaluator, visibility policy, or required context-reference failure is not an acceptable diagnostic.
  - Replacing one vendor-specific music tool name with another hard-coded provider name is not supplier decoupling.
- Execution order:
  - A2.0: freeze the authority matrix, identity matrix, static import closure, dynamic construction sentinel, and known failing tests before implementation.
  - A2.1: introduce the versioned project-definition port/UoW and SQLAlchemy adapter; migrate authored fields and remove runtime fields from project authority.
  - A2.2: add the immutable project-execution projection and migrate API/queue readers without dual writes.
  - A2.3: replace the episode Agent with the application coordinator and inject runtime ports into the MAS control-plane orchestrator.

### Amendment A3 - Report/gate convergence and strict acceptance closure
