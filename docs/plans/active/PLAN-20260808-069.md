## 3. Implementation Approach
- **Fallback 设计准则（2026-08-09 用户确认，全计划规范，063 Stage E 的彻底化）**：
  fallback 不得作为代码内的静默 else 分支存在。任何主路径失败必须：
  ① 以结构化错误上抛（ToolError/AgentError 携带 error_code 与诊断细节），
  ② 成为 ReAct 轨迹（trajectory）的一部分——失败作为 observation 进入下一轮上下文，由 LLM 决定重试/调参/显式选用默认值，
  ③ 可观测——结构化诊断进事件/遥测，不允许仅 logger.warning 后静默继续。
  确定性代码替 LLM 补一个"看起来合理"的结果 = 伪造，一律禁止。显式默认值只能由 LLM 在轨迹内主动选择，不能由工具静默代选。
- Patch strategy: 三个 Sprint 顺序推进，每个 Sprint 内条目独立可验证、可单独提交。
  - **S1-3 前置考证**：L114-120 的 completed-only 校验疑似近期治理提交（b6c6f32 "enforce exact continuation contracts" / 58da249 "coordinate publication and terminal success"）刻意引入。修复前先 git log 考证设计意图；修复方向是**拆分关注点**——信封校验只验结构与枚举合法性，"终态成功裁定必须 completed" 只保留在 runtime success finalization 闸门处，partial 报告放行至 `_llm_decide_runtime_decision` 由编排 LLM 裁决（重试/带缺口继续/失败），而非在协议层一刀切抛错。

### A1.1 Thin module contracts and decision ownership
- Agent report 是专业 Agent 的事实输出，只声明一个 canonical `status`：`completed`、`partial` 或 `failed`。协议层只解析结构、JSON 类型、枚举与 provenance，不决定工作流是否成功。
- Runtime disposition 是控制面的独立结构化输出：非成功报告只能选择 `retry_current`、`activate_from_standby`、`accept_with_gaps`、`abort`；既有 completed gate 决策保留显式 `continue`。LLM 直接以 `response_format={"type":"json_object"}` 产生该对象；控制面只验证动作、target、budget 和状态转换不变量。
- `completed` 才能进入当前 success finalization。`partial` / `failed` 以及可处置的 Agent/Tool failure observation 必须在任何 workflow map、shared fact、deliverable 或 attempt-success 写入之前，无条件进入 disposition；不得因 gate/standby 为空自动 `continue`。
- `failed` 禁止 `accept_with_gaps`。`partial` 只有在 LLM 显式选择 `accept_with_gaps` 且报告携带非空 `reported_gaps` 时，才可使用既有 `completed` 终态完成 promotion，并保留 gaps/decision receipt；不得新增 `completed_with_gaps` 或第二完成状态。
- Contract integrity、malformed JSON、非法 action/target 与缺失 authority 直接 fail closed，不进入重试 fallback。可恢复执行失败以 typed observation 进入 LLM 轨迹；删除 `_should_retry_step` 的异常类名/子串启发式。

### A1.2 No fabricated fallback and LLM-owned semantic decisions
- 活跃或可被生产注册表暴露的 LLM JSON 路径必须请求 JSON object、单次解析、失败抛 typed `ToolError` / `AgentError`。删除正则 JSON 提取、成功形态默认结果、固定 confidence/score 和静默 logger-only continuation。
- 移除 VideoGenerator 自动依赖的关键词 `scene_analysis` 语义工具；场景复杂度、动作密度、节奏与连续性策略归 Specialist Agent/LLM。确定性代码只保留产物存在性、类型、provider capability、预算和显式政策门禁。
- `scene_continuity_analysis_tool`、`script_generation_tool` 和 provider JSON clients 的失败必须成为 ReAct observation，不得编造独立生成策略、叙事结构或连续性分数。
- `parameter_optimization` 当前未分配给生产 Agent：先从生产注册/暴露面注销；若未来重新启用，必须由 LLM 结构化输出直接决定并通过新验收，不保留字符长度 fallback。
- QualityChecker 的主观质量判断必须消费 LLM 结构化评估；固定布尔比例、语义权重和风格子串不得决定审批。media completeness、role-continuity hard gate 与配置化政策阈值仍由确定性 gate 执行。LLM 不可用时 Agent 如实返回 `partial` + typed gap，不补造分数。PLAN-065 继续拥有角色连续性维度与阈值语义；本 Amendment 只拥有 LLM 评估接入、失败合同和 anti-agentic 规则移除。
