## 0. Background
2026-08-08 的 anti-agentic 多维审查（5 维度、29 条发现、13 条经对抗验证 confirmed）表明：
mas-boundary-cleanup 后核心执行链（orchestrator LLM 路由、运行时控制面 SOT、ReAct 契约、domain 纯净度）健康，
但质量评估链路仍被规则实质接管，协议层封杀合法 partial 上报会导致工作流硬失败，另有一批可被误接回的
anti-agentic 死代码残留。本计划按 S1（high 修复）→ S2（medium 修复）→ S3（死代码清理）三个 Sprint 收口。

## 1. Current Problem
- Symptom:
  1. quality_checker 最终审批完全由规则打分决定（布尔项通过比例 + 硬编码权重 0.3/0.4/0.3 + 阈值 90/80/70/60），LLM 内容分析结果仅作 `ai_analysis` 附件、对审批零影响；LLM 失败时主观维度全按"通过"计分且无降级信号（`backend/app/agents/quality_checker.py:485,1003,1042,1073`）。
  2. parameter_optimization_tool 用 `if False:` 永久禁用 LLM 分析消费分支，时长决策被"文本>200字符用最长否则最短"启发式接管，LLM 调用照常消耗 token 但判断被 100% 丢弃（`backend/app/agents/tools/ai_services/parameter_optimization_tool.py:243,420`）。
  3. orchestration_protocol.build_subagent_report 先接受 {completed, partial, failed} 枚举（L107），又对非 completed 一律抛 OrchestrationProtocolError（L114-120）；audio_generator（L181）与 video_generator（L679）的诚实 partial 上报会被包装成 `_OrchestrationBoundaryError`，不匹配 `_should_retry_step` 的重试规则，直接导致工作流硬失败；现存的 `_llm_decide_runtime_decision`（orchestrator.py:2102）永远收不到 partial 报告。
  4. Medium 级确认问题 8 项与死代码残留 6 项，详见 S2/S3 清单。
- Impact: 语义质量判断被结构规则接管（LLM 评估形同虚设）；部分完成的合法产出直接引发全流程失败；编排 LLM 的运行时裁量权被架空；死代码存在被后续开发误接回的风险。
- Reproduction: 见审查证据（各条目 file:line 已列）；S1-3 可用 bgm 生成失败场景复现（audio_generator 上报 partial → 协议抛错 → 工作流硬失败）。

## 2. Deviation Analysis
- Expected behavior: 语义/创意/质量判断由 LLM 驱动，确定性代码只做硬门禁（产物存在性、media completeness、role continuity score cap）；agent 如实上报 partial 后由编排 LLM 裁决处置；契约缺失 fail-fast 而非静默兜底；每个事实只有一个写入方。
- Actual behavior: 见 Current Problem。
- Root cause hypothesis: mas-boundary-cleanup 系列重构完成了编排/运行时控制面的治理，但质量评估链路与外围工具未纳入同批治理范围；orchestration_protocol 的 completed-only 校验把"终态成功裁定"（编排策略）硬编码进了自称不做编排决策的信封层。

## 3. Implementation Approach
- Patch strategy: 三个 Sprint 顺序推进，每个 Sprint 内条目独立可验证、可单独提交。
  - **S1-3 前置考证**：L114-120 的 completed-only 校验疑似近期治理提交（b6c6f32 "enforce exact continuation contracts" / 58da249 "coordinate publication and terminal success"）刻意引入。修复前先 git log 考证设计意图；修复方向是**拆分关注点**——信封校验只验结构与枚举合法性，"终态成功裁定必须 completed" 只保留在 runtime success finalization 闸门处，partial 报告放行至 `_llm_decide_runtime_decision` 由编排 LLM 裁决（重试/带缺口继续/失败），而非在协议层一刀切抛错。
  - **S1-1 quality_checker**：`_generate_quality_assessment` 改为消费 `_ai_content_analysis` 的 LLM 评估结果（叙事连贯性/信息清晰度/受众适配等主观维度由 LLM 打分并给出理由）；确定性检查仅保留硬门禁角色（media completeness 翻转、role continuity score cap 维持现状）；LLM 分析失败时不再静默按通过计分，而是封顶 overall_score 并强制 `requires_human_review=True`，同时在 orchestration_report 的 reported_gaps 中显式上报 `ai_analysis_unavailable`。移除 L1042 的风格子串匹配（风格符合性并入 LLM 评估维度）。
  - **S1-2 parameter_optimization_tool**：删除 `if False:` 恢复 LLM 分析消费分支；`_fallback_duration_optimization` 仅在 LLM 调用/解析失败时走，且结果必须显式标注 `fallback_method=True` 并降低 confidence，调用方可感知。
- Compatibility considerations:
  - S1-3 改动影响所有子 agent 上报路径，需保证 completed 主路径行为不变（现有 A6 验证与 continuation contract 测试必须全绿）；partial 的 LLM 裁决新增分支不得绕过 `runtime_gate_control_plane` 既有闸门。
  - S1-1 改变 quality_checker 输出分数分布，`orchestrator` 对 quality 报告的消费（L954-965 的 final_video 硬闸）不受影响；需确认无下游对具体分值阈值的硬依赖。
  - S2-5 前端枚举收敛涉及 API 表面，保持 kebab-case id 对外不变，仅收敛映射源。
- Rollback plan: 每个条目独立 commit，出问题按条目 revert；S1-3 若考证发现 completed-only 是被冻结的刻意契约且不可拆分，则降级为"orchestrator 侧捕获 `_OrchestrationBoundaryError` 中 reason_code=orchestration_report_not_successful 的分支并转交 LLM 裁决"，协议层不动。
